# ระบบสารบัญ — Decisions

## D1: ใช้ Apps Script แทน Node/Python backend
**เหตุผล**: ไม่ต้องมี server แยก, deploy ฟรีบน Google, ใช้ DriveApp ได้โดยตรง, ทีมคุ้นเคยกับ pattern เดียวกับระบบออมทรัพย์

## D2: ~~ใช้ LINE OA ตัวเดียวกับระบบลงเวลา~~ — เลิกใช้ร่วมแล้ว (2026-07-01)
**เหตุผลเดิม**: ประหยัด, LINE OA 1 ช่องส่งได้หลาย Group และหลายระบบพร้อมกัน แค่ใช้ Channel Access Token เดิม
**อัปเดต 2026-07-01**: แยก channel แล้ว — ระบบลงเวลาสร้าง LINE OA ใหม่ของตัวเอง (token เก็บใน Supabase SQL function) เพราะสองระบบแย่ง quota กันจนหมดกลางเดือน (429) ระบบสารบัญยังใช้ channel เดิม (token ใน `Code.gs`) เป็นระบบเดียวแล้ว
**ผลตกค้าง**: ตอนแยกวันที่ 2026-07-01 quota ของ channel นี้เหลือ **11/300** (ใช้ไป 289) — สาเหตุที่แน่ชัดยังไม่ยืนยัน (การแย่งกันมาก่อนเป็นแค่หนึ่งในสองทฤษฎี) รายละเอียด+ทฤษฎีที่สอง ดู BUG-D11 ใน known-bugs.md

## D3: ส่ง LINE Group (textV2 mention) เท่านั้น — ไม่ส่ง DM
**เหตุผล (อัปเดต มิถุนายน 2569)**: เดิมส่ง DM รายคนด้วย แต่ LINE Messaging API push message นับ quota (300/เดือน ฟรีเทียร์) และ reply ไม่นับ ครูทุกคนได้รับ notification ผ่าน @mention ใน group แล้ว การส่ง DM ซ้ำซ้อนและเปลือง quota
**การเปลี่ยนแปลง**: `sendLineDM()` ใน Code.gs ยังอยู่แต่ถูก comment out ทั้งบล็อก สามารถ uncomment คืนได้ถ้าจำเป็น

## D4: ดึงชื่อจริงจาก LINE Profile API ตอนส่ง
**เหตุผล**: ชื่อในระบบ (`TEACHERS[].name`) อาจไม่ตรงกับชื่อ LINE ของครู การดึง displayName จาก API ทำให้ข้อความ @mention ตรงกับที่เห็นในกลุ่มเสมอ

## D5: Base64 file upload ผ่าน JSON body
**เหตุผล**: Apps Script Web App รับ multipart/form-data ได้ไม่ดี, JSON + base64 ทำงานได้เสถียรกว่า ขนาดสูงสุด 20 MB (Drive อนุญาต)

## D6: subfolder ตามปีการศึกษา/ปีปฏิทิน
**เหตุผล**: ง่ายต่อการค้นหาย้อนหลัง, สร้างอัตโนมัติถ้าไม่มี ไม่ต้องสร้างมือ

## D7: ชื่อไฟล์บน Drive = ชื่อเรื่อง + นามสกุลเดิม
**เหตุผล**: ค้นหาได้ง่ายกว่าชื่อไฟล์ต้นฉบับที่มักเป็น `scan001.pdf`
```js
var safeName = title.replace(/[/\\?%*:|"<>\r\n]/g, '_') + '.' + ext;
```

## D8: ไม่มี login / authentication
**เหตุผล**: ระบบใช้ในโรงเรียน URL ไม่เปิดเผย ผู้ใช้คือเจ้าหน้าที่ธุรการเท่านั้น ความง่ายใช้งานสำคัญกว่า
**หมายเหตุ**: risk ที่ยังค้างอยู่ใน RISK-01 ของ known-bugs.md — ถ้า URL รั่วออกไปมีคนส่ง spam LINE group ได้ แก้ได้โดยเพิ่ม shared secret header

## D9: Webhook mode สำหรับหา userId — ปิดแล้ว
**เหตุผล**: userId ครูทุกคนได้มาครบแล้ว (มิถุนายน 2569) Webhook mode ถูก comment out ทั้งบล็อกใน `doPost` แล้ว
**ถ้าต้องการใช้อีก**: uncomment block ใน `doPost` ของ Code.gs, deploy ใหม่, รับ userId แล้ว comment กลับและ deploy อีกครั้ง

## D10: ไปราชการ/อบรม แยกออกจาก "วันลา" ในสรุป LINE
**เหตุผล**: การไปราชการ/อบรม/ประชุม/ศึกษาดูงาน ไม่ใช่วันลาจริง แต่ครูไม่อยู่โรงเรียน ควรแสดงแยกให้ชัดเจน
**การ implement**: ใช้ `duty_types TEXT[] := ARRAY['ไปราชการ','อบรม','ประชุม','ศึกษาดูงาน']` ใน Supabase function
— `leave_type = ANY(duty_types)` → 🚌 ราชการ/อบรม
— `leave_type <> ALL(duty_types)` → 🏖️ ลาจริง

## D11: Year selector ใช้ BASE=2566 เพิ่มอัตโนมัติ
**เหตุผล**: ไม่ต้องแก้โค้ดทุกปี loop จาก `thaiYear + 1` ลงถึง BASE=2566 เพิ่มปีถัดไปอัตโนมัติเมื่อถึงปีนั้น

## D12: Code.gs อยู่ใน .gitignore — ไม่ commit ลง git
**เหตุผล**: Code.gs มี LINE_TOKEN จริง การ commit จะทำให้ token อยู่ใน git history ตลอดไป แม้จะลบในภายหลัง
**การจัดการ**: เก็บ Code.gs ไว้ใน `School Portal/ระบบสารบัญ/` (local) โดยไม่ commit — paste เข้า GAS editor โดยตรงเมื่อต้อง deploy

## D13: [SUPERSEDED BY D14] กลับมาใช้ DM สำหรับเลือกครูเฉพาะเจาะจง — แก้ D3 (2026-07-08)
> ⚠️ **เลิกใช้แล้วในวันเดียวกัน** — โค้ด DM/mention ทั้งหมด (`sendLineGroup`/`sendLineDM`/`notifyLine`) ไม่ถูกเรียกจาก production flow อีกต่อไป ดู D14 สำหรับสถานะปัจจุบันจริง (สรุปรวมตอนเย็น) เก็บ entry นี้ไว้อธิบายเหตุผลที่เคยคิดแบบนี้ก่อนเจอปัญหาความถี่
**เหตุผลของ D3 เดิม** (ยกเลิก DM, ใช้ group mention อย่างเดียว): คิดว่า DM ซ้ำซ้อนกับ group mention และเปลือง quota กว่า
**พบว่า D3 เข้าใจผิด**: ตรวจสอบกับ LINE official docs (developers.line.biz/en/docs/messaging-api/pricing) แล้วพบว่า LINE คิด credit ตาม **จำนวนคนที่ได้รับข้อความจริงในแชทนั้น** ไม่ใช่ตามจำนวนครั้งที่ยิง API — push เข้ากลุ่ม 1 ครั้งหักเครดิตเท่าจำนวนสมาชิกทั้งกลุ่มเสมอ (กลุ่มนี้ 15+ คน) ไม่ว่าจะ mention กี่คนก็ตาม ในขณะที่ DM ตรงถึงคนที่เลือกจริงคิดแค่ 1 เครดิต/คน — เกิดเหตุการณ์จริง 2026-07-08: badge บอกเหลือ 9 เครดิต แต่ส่งไม่ได้เลย เพราะ 9 ไม่พอสำหรับ push เข้ากลุ่ม (~15-17 เครดิต/ครั้ง) ทั้งที่พอสำหรับ DM ได้อีกหลายคน
**การเปลี่ยนแปลง**: เพิ่ม `notifyLine()` เป็น router ใหม่ — mentionAll=true (แจ้ง @ทุกคน) ยังใช้ `sendLineGroup()` เหมือนเดิม (เท่ากันอยู่แล้วไม่เสียเปรียบ), เลือกครูเฉพาะเจาะจง (mentionAll=false) → ใช้ `sendLineDM()` ใหม่ ส่งตรงถึงคนที่เลือกเท่านั้น ประหยัด credit กว่าเสมอ (ยกเว้นเลือกครบทุกคนพอดี)
**Trade-off ที่ยอมรับแล้ว**: เอกสารที่เลือกครูเฉพาะเจาะจง จะไม่ขึ้นในกลุ่มให้ครูคนอื่นเห็นอีกต่อไป (เสีย shared visibility เดิม) — Pam เลือกวิธีนี้เพราะเน้นรักษา credit ให้ส่งได้เยอะที่สุดก่อน (2026-07-08)
**ยังไม่ deploy**: แก้ใน local `Code.gs` แล้ว รอ Pam paste เข้า GAS editor

## D14: เปลี่ยนจากแจ้งทันที (D13) เป็นสรุปรวมส่งตอนเย็น 16:00 — แก้ D13 อีกที (2026-07-08)
**เหตุผลของ D13 ที่พบว่ายังไม่พอ**: ทดลองคำนวณแล้วพบว่า DM ต่อเอกสารยังเสี่ยงชนเพดาน 300/เดือนถ้าโรงเรียนส่งเอกสารบ่อย (แม้จะถูกกว่า group broadcast) เพราะทุกครั้งที่ "ส่ง" (ไม่ว่า DM หรือ group, mention หรือไม่) หัก credit ตามจำนวนคนที่ได้รับข้อความเสมอ — ตัวแปรที่ลด credit ได้จริงคือ "ความถี่ที่ส่ง" ไม่ใช่วิธี mention
**การเปลี่ยนแปลง**: ยกเลิกการส่ง LINE ทันทีตอนอัปโหลดทั้งหมด (ทั้ง DM และ group) เปลี่ยนเป็น:
- ทุกครั้งที่อัปโหลดเอกสาร → บันทึกคิว (เรื่อง, ลิงก์, ครูที่ได้รับ) ลง Google Sheet ใหม่ "ระบบสารบัญ - บันทึกประจำวัน" แทน (ไม่ยิง LINE เลย ณ จุดนี้)
- Time-based trigger รันทุกวัน 16:00 (`sendDailySummary()`) — อ่านคิววันนั้น สรุปเป็นข้อความเดียว **ไม่ mention ใครเลย** เรียงตามลำดับเอกสาร ส่งเข้ากลุ่ม 1 ครั้ง แล้วเคลียร์คิว
- วันไหนไม่มีเอกสารเลย → ข้าม ไม่ส่งอะไร (ประหยัด credit สูงสุด ตามที่ Pam เลือก 2026-07-08)
- หน้าเว็บอัปโหลด (index.html) ไม่เปลี่ยนแปลง — ครูยังเลือกผู้รับต่อเอกสารเหมือนเดิมทุกอย่าง แค่ backend ไม่ยิง LINE ทันทีอีกต่อไป (เปลี่ยนข้อความ success เป็น "บันทึกคิวแล้ว จะสรุปตอน 16:00")
**Trade-off**: ครูไม่ได้รับแจ้งทันทีอีกต่อไป (ต้องรอถึง 16:00) และไม่มี real mention/ไฮไลต์ชื่อในสรุปเลย — Pam ยอมรับแล้วเพื่อรักษา credit ให้ส่งได้เยอะที่สุด
**ผลต่อ credit**: จากคิดตาม "จำนวนเอกสาร" → คิดตาม "จำนวนวันที่มีเอกสาร" (~1 ครั้ง/วันสูงสุด แทนที่จะเป็นทุกเอกสาร) — ยังคงต้องเฝ้าระวังถ้าโรงเรียนมีเอกสารเกือบทุกวันทำการ เพราะ 300÷~15-17 คน ≈ 18-19 ครั้ง/เดือนเท่านั้น ยังปริ่มเพดานถ้าส่งครบทุกวันทำการ
**ยังไม่ deploy**: แก้ local `Code.gs`+`index.html` แล้ว รอ Pam paste + ตั้ง trigger (`setupDailyTrigger()`) ครั้งเดียว

## D15: Badge แสดง "ส่งได้อีกกี่วัน" ไม่ใช่แค่ credit ดิบ (2026-07-08)
**เหตุผล**: credit ดิบ (เช่น "เหลือ 9") ทำให้เข้าใจผิดว่าส่งได้อีก 9 ครั้ง ทั้งที่จริงต้องหารด้วยจำนวนคนในกลุ่มก่อน (ดู D13/D14)
**การเปลี่ยนแปลง**: `getLineQuota()` เพิ่มเรียก LINE API `/v2/bot/group/{groupId}/members/count` (ดึงจำนวนสมาชิกกลุ่มจริงสด ไม่รวมบอท) คำนวณ `sendsRemaining = floor(remaining / groupSize)` ส่งกลับไปด้วย — badge หน้าเว็บโชว์ "ส่งสรุปได้อีก ~N วัน จากกลุ่ม M คน" ควบคู่ตัวเลข credit ดิบ และใช้ `sendsRemaining` ตัดสินสี badge (เขียว/เหลือง/แดง) แทน credit ดิบ
**ยังไม่ deploy**: อยู่ใน local `Code.gs`+`index.html` แล้ว รอ paste พร้อมของ D14

## D16: สรุปตอนเย็นเปลี่ยนปลายทางจาก "เข้ากลุ่ม" เป็น "DM หา ผอ. คนเดียว" — แก้ D14 (2026-07-10)
**เหตุผล**: Pam ตัดสินใจให้สรุปตอนเย็นส่งหา ผอ. (นายภานุวัฒน์ คลังสิน) คนเดียวเท่านั้น ไม่เข้ากลุ่มอีกต่อไป — นอกจากตรงกับ workflow ที่ต้องการ (ผอ.เห็นภาพรวม ไม่ต้องรบกวนครูทุกคนทุกวัน) ยังแก้ปัญหา quota แบบเบ็ดเสร็จไปด้วย เพราะ DM 1 คน = 1 เครดิต/ครั้งเสมอ (เทียบกับ push เข้ากลุ่มที่หักเท่าจำนวนสมาชิกกลุ่มทุกครั้ง ~15-17 เครดิต — ดู D14/D15) วันละครั้งใช้แค่ 1 เครดิต/วัน เดือนหนึ่งใช้ไม่ถึง 31 เครดิต จาก 300 ที่มี ไม่ต้องกังวลเรื่อง quota อีกแล้วในทางปฏิบัติ
**การเปลี่ยนแปลง**:
- เพิ่ม `DIRECTOR_NAME` ใน CONFIG (Code.gs) — หา userId จาก `TEACHERS` array ที่มีอยู่แล้วด้วย `findTeacher()` ไม่ต้องเก็บ userId ซ้ำอีกที่ ถ้าเปลี่ยน ผอ. ในอนาคตแก้แค่ชื่อนี้ให้ตรงกับ entry ใน `TEACHERS`
- `sendDailySummary()` เปลี่ยน `to: LINE_GROUP` เป็น `to: director.userId` — ถ้าหาชื่อใน TEACHERS ไม่เจอ (พิมพ์ไม่ตรง) จะ log error และไม่ clear คิว รอรอบถัดไป ไม่ throw/พัง
- `getLineQuota()` ตัดการเรียก `/members/count` ออก (ไม่จำเป็นแล้ว) `sendsRemaining = remaining` ตรงๆ เพราะ DM 1 คน = 1 เครดิตเสมอ ไม่ต้องหารด้วยขนาดกลุ่มอีก
- badge หน้าเว็บ (index.html) ข้อความเปลี่ยนจาก "จากกลุ่ม N คน" เป็น "DM หา ผอ. คนเดียว"
- `LINE_GROUP` ยังเก็บไว้ใน Code.gs เพราะ `fetchDisplayNames()` (ดึงชื่อ LINE จริงมาโชว์ตอนเลือกครูในหน้าเว็บ) ยังใช้อยู่ — ไม่เกี่ยวกับการส่งสรุปแล้ว
**ยังไม่ deploy**: แก้ local `Code.gs`+`index.html` แล้ว รอ Pam paste+deploy (ไม่ต้องตั้ง trigger ใหม่ ถ้าเคยรัน `setupDailyTrigger()` แล้วตาม D14 — trigger เดิมยังชี้ไปที่ `sendDailySummary()` ตัวเดิม แค่เนื้อในฟังก์ชันเปลี่ยนปลายทาง)

## D17: ส่งสรุปเฉพาะวันทำการ (จันทร์-ศุกร์) — เสาร์-อาทิตย์ข้าม (2026-07-11)
**เหตุผล**: เสาร์-อาทิตย์ปกติไม่มีธุรการอัปโหลดเอกสารอยู่แล้ว แต่ถ้ามีอัปโหลดเข้ามาโดยบังเอิญ (เช่น งานเร่งด่วน) ไม่จำเป็นต้องส่งสรุปแยกวันหยุด — รวมไปกับวันทำการถัดไปได้เลย ประหยัด credit เพิ่มอีกเล็กน้อย (สูงสุดจากทุกวัน 30-31 ครั้ง/เดือน เหลือแค่ ~22 ครั้ง/เดือน เท่าจำนวนวันทำการ)
**การเปลี่ยนแปลง**: `sendDailySummary()` เช็ควันแรกสุดก่อนแตะ lock/sheet ใดๆ เลย ด้วย `Utilities.formatDate(new Date(), 'GMT+7', 'u')` (ISO day-of-week, 6=เสาร์ 7=อาทิตย์) ถ้าตรงวันหยุด `return` ทันที ไม่ clear คิว — เอกสารที่ค้างจะถูกรวมส่งพร้อมวันทำการถัดไปอัตโนมัติโดยไม่ต้องแก้อะไรเพิ่ม (กลไกเดิมของ "ไม่ clear คิวถ้าไม่ได้ส่งสำเร็จ" รองรับอยู่แล้ว)
